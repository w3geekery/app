**Current Half-A method stubs to rewrite:**
1. `listProviders(orgId?: string, pageSize?: number)` — returns `Promise<ProviderDirectoryRow[]>`
2. `searchProviders(query: string, pageSize?: number)` — returns `Promise<ProviderDirectoryRow[]>`
3. `getProvider(orgId: string)` — returns `Promise<ProviderDetailRow>`
4. `getProviderByUserId(userId: string)` — returns `Promise<ProviderProfile>`

**New signatures (retargeted types):**
All methods query `OrgProfile` + the 6 expertise junctions via GQL nested selections. Return types become GQL response objects (internal to service) which are then transformed into display rows by `buildSections()` and projection helpers.

**Implementation pattern (from PATTERNS.md):**
1. Build a GQL query string with nested selections over `OrgProfile` + `ProviderSkill` + `ProviderRole` + `ProviderProduct` + `ProviderFramework` + `ProviderSegment` + `ProviderServiceSegment` (all 6 junctions). Query shape per RESEARCH.md §2.1–2.8, fields: `id`, `orgId`, `*Id` (Catalog FKs), profession-level/years fields, `verified`, `verificationSource`.
2. Call `boundaryExecuteRawQuery` with the nested query (same pattern as current lines 59–75).
3. Transform the GQL response into display objects using `buildSections()` and name-resolution helpers.
4. For `listProviders` (list view): Return a lighter projection (directory row with name, headline, avg rating, segment count).
5. For `getProvider` (detail view): Return full expertise sections (resolved names, verified status).
6. For `getProviderByUserId`: Query by the `primaryContactUserId` field on `OrgProfile` (new in typed model).

**Dropped-field removal (§7 #3):** Delete projections of `hourly_rate`, `availability_status`, `response_time` from any return shapes or SELECT clauses (typically lines ~104-106 if present). These fields are deleted from the schema per D-57 #3; do NOT project them.

**Return-shape design decision (state in task completion):** The new `getProvider`/`getProviderByUserId` return shape SHOULD expose an `id` (or `orgId` aliased to `id`) so the ~7 downstream `.id`-only callers (engagement-detail, engagement-list, rfp-detail, bid-wizard, my-profile-services, my-profile-reviews, my-profile-moderate-reviews) compile unchanged. If you choose NOT to expose `id`, those callers all need edits in 33-06 — call it explicitly either way in the done criteria.

**Name resolution pattern:**
Instead of denormalized `*_name` fields in the GQL response, resolve names on read:
```typescript
const skillName = this.catalog.findSkill(row.skillId)?.name || '(unknown)';
```
The `CatalogService` is already injected (see current code). The find* helpers (`findSkill`, `findRole`, `findProduct`, `findFramework`, `findSegment`) are pre-loaded async methods that return Catalog records by UUID; cache them or load on mount.

**Neon VIEWs removal:**
Delete any references to `v_provider_directory` and `v_provider_detail` (Neon VIEW names). These are the current queryMpi internals; they're replaced by GQL nested selections.

**Method-by-method guidance:**

- `listProviders(orgId?, pageSize?)`: Query all OrgProfile rows (optionally filtered by orgId if provided); for each, load the expertise junctions and build a `ProviderDirectoryRow` with org name, headline, avg rating from Review aggregate, segment names resolved. Return array. Expose `id` if possible.
- `searchProviders(query, pageSize?)`: Query OrgProfile with a text filter (name/tagline/shortDescription contains query); load expertise; build directory rows; return array. Expose `id` if possible.
- `getProvider(orgId)`: Query single OrgProfile by orgId; load all expertise junctions; build full `ExpertiseSection[]` with resolved names; return a detail row object. Expose `id` / `orgId`.
- `getProviderByUserId(userId)`: Query OrgProfile where primaryContactUserId = userId; load expertise; return detail. Expose `id` / `orgId`.

**Error handling:**
Wrap GQL calls in try/catch (see notes.service.ts for pattern); log errors to console; do NOT surface to snackBar (half-A is read-only; caller decides presentation).

**Angular 21 compliance:**
Use `inject()` for CatalogService (not constructor injection). Mark methods as `readonly`. Use const assertions where applicable. Remove @deprecated decorators if present.
