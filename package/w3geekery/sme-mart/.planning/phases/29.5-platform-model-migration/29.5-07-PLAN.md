## Locked decisions
- **D-34:** Vetting Board name = "Vetting Board" (exact, locked)
- **D-35:** Vetting Board description = "Vetting items for {engagement.name}" (exact template, locked)
- **D-04 / D-36:** Board governance model: ownerId = engagement Project UUID (not org), scoped to engagement
- **D-37:** Vetting paired-task shape (γ) — parent + one subtask per side; activityId on parent ties to vetting workflow
- **D-45:** 3P verification gates may NOT depend on ZB internal UI surfaces. Verification at SDK contract + SME Mart's own UI.

## Platform.Board + Task SDK contract expectations
- **Board creation:** `platform.Board.create` returns BoardExtended with id, name, description, ownerId
- **Board round-trip:** `platform.Board.get(id)` returns same shape; `ownerId` equals engagement Project UUID
- **Task on Board:** `platform.Task.create` with appropriate Board reference (per Plan 02 verified contract)
- **Paired-task shape:** parent vetting Task + one subtask per side (per D-37); both reachable via `platform.Task.get`
- **SME Mart consumer pathway:** Vetting view consumes `platform.Board` + `platform.Task` via SDK to render its own UI

## Failure handling
- If `platform.Board.create` fails or shape diverges → Plan 02 Step D bug; fix in place
- If paired-task shape doesn't round-trip cleanly → Plan 02 or vetting Task creation logic bug; fix in place
- If SME Mart Vetting view fails to render Board + Tasks correctly → SME Mart consumer bug (Vetting view component / service); fix in place
- **No conditional backlog entries targeting ZB Phase 32 / ZB UI rendering.** Failures are bugs in our own work; D-34–D-37 stay locked.
