# Phase 29.5: Platform Model Migration - Context

**Gathered:** 2026-05-08
**Status:** Ready for planning

<domain>
## Phase Boundary

Replace SmeMart's GraphQL-class-based modeling of Engagements, Projects, Boards, and engagement-vetting with the new platform / portal / hydra SDK primitives announced 2026-05-08 (`@zerobias-com/platform-sdk@1.1.16`, `@zerobias-com/portal-sdk@1.1.16`, `@zerobias-com/hydra-sdk@1.0.7`, `@zerobias-com/zerobias-mcp@1.0.43`).

**In scope:**
- Provisioning recipe rewrite: 7 steps → 5 steps (B/E removed; C/D/F/G updated). Engagement-as-Project hierarchy locked; identity tag attached at create via `Project.tagId`; vetting Board lazy-created.
- Service refactors: `engagements.service.ts` swaps GQL `Engagement` reads → `platform.Project.list({ ownerId, tagId-classifier-filter })`. `SmeMartProjectService` keeps its name; implementation flips from `Pipeline.receive(SmeMartProject)` + GQL reads to `platform.Project.list/get/create/update`.
- GQL retirement: `Engagement`, `EngagementVettingItem`, `SmeMartProject` deprecated without delete in `zerobias-org/schema` (Daniel Rojas PR review). Dual-read until data ages out.
- Buyer-side My Engagements: implement on new shape (`platform.Project.list({ ownerId: <buyerOrgId> })`).
- Resource-type handling: surface `project` and `board` `ResourceTypeEnum` values in demo-visibility post-filter, resource-link rendering, and navigation.
- Governance verification gate (UAT smoke): provision a test org, confirm ZB Platform Governance UI surfaces `platform.Project` records.
- Vetting Board pattern smoke: manually create one paired vetting Task on a test engagement Project; confirm parent + subtask shape lands cleanly with `boardId` server-default chain.

**Out of scope:**
- Provider-side My Engagements UI (spec query shape only; backlog `PROVIDER-MY-ENGAGEMENTS-1`).
- New features beyond model migration.
- Activity-workflow definitions for vetting requirement types (insurance, ToS, MSA, background-check) — authored later when concrete requirements land.
- Hub-side data migration / one-shot backfill (not happening; dual-read instead).
- UI redesigns (customer-facing noun stays "Engagement"; Project is persistence-only).
- Renaming `SmeMartProjectService` → `ProjectService` (organic cleanup; backlog `PROJECT-SVC-RENAME-1`).
- Schema-class deletion (post-v1.4 follow-up; backlog `SCHEMA-RETIREMENT-DELETE-1`).
- Phase 30 brief refresh (Director artifact, not a 29.5 deliverable).
- PERMS-AUDIT-1 implementation (separate phase; hydra Role scoped-grant primitives now exist).
- `EngagementMetadata` GQL class creation (planted seed for v1.5+).

<decisions>
## Implementation Decisions

### Engagement-as-Project hierarchy (Path C — LOCKED)

- **D-01:** Engagement IS a top-level `platform.Project` record (`parentId=null`). Workspace is a child Project (`parentId=engagement.id`). Vetting Board is an immediate-child Board on the engagement Project (lazy-created on first vetting requirement; not eager).
- **D-02:** Workspace child Project is **tagless** (`tagId=undefined`). Identity tag rides the engagement Project only. Engagement remains the single tag-search entry point; avoids tag duplication.
- **D-03:** Engagement Project `ownerId = buyerOrgId` (buyer-anchored ownership). Provider-side discovery for v1.5+ via membership + tag classifier (out of scope for 29.5 UI).
- **D-04:** Engagement Project `parentId=null` for v1.4 — top-level orphan; no nesting under a ZB-org parent.
- **D-05:** Customer-facing noun stays "Engagement". The `platform.Project` record is persistence-only — users never see "Project" on the engagement-detail page. Locked verbiage from 2026-05-07 EVE preserved verbatim (see `Verbiage` section below).

### Provisioning recipe — 5 steps (was 7)

- **D-06:** Recipe collapses to 5 steps. Step labels preserved with skips marked so DECISIONS / commits can reference history cleanly:
  - **A:** `hydra.Tag.create` — identity tag `sme-mart.eng.zerobias-to-{slug}` (owned by `MARKETPLACE_OPERATOR_ORG_ID`).
  - ~~**B:**~~ ~~Engagement Task (`aha1-N`)~~ — DROPPED. `Project.status` enum + Governance-Project-rendering replaces both lifecycle and Governance surfacing roles. Verification gate is a 29.5 deliverable (D-08).
  - **C:** `platform.Project.create` — engagement Project. `parentId=null`, `ownerId=buyerOrgId`, `tagId=A.id`, `name="${orgName} <- ZeroBias"`, `description="Platform Services Engagement: ZeroBias ➡️ ${orgName}"` (no trailing period), `status='active'`, `visibility='internal'`, `membershipPolicy='private'`.
  - **D:** `platform.Project.create` — workspace Project. `parentId=C.id`, `ownerId=buyerOrgId`, `tagId=undefined`, `name="ZeroBias Platform"`, `description="${orgName}'s gateway into ZeroBias — tasks, notes, and communication tied to the ZeroBias ➡️ ${orgName} platform engagement live here."`, `status='active'`, `visibility='internal'`, `membershipPolicy='private'`.
  - ~~**E:**~~ ~~`Pipeline.receive` — link Engagement to Project + tag-attach~~ — DROPPED. `Project.tagId` built-in eliminates the round-trip; Engagement-as-Project means no separate Engagement record to link.
  - **F:** `platform.Board.create` — default kanban Board on workspace Project. `projectId=D.id`, `name="ZeroBias Platform"`, `status='active'`, `boardType='kanban'`, `isDefault=true`.
  - **G:** `platform.Project.addMember` — add admin user as member of engagement Project. Buyer-org admin user becomes engagement member. Provider-side membership added separately (out of scope for 29.5; relevant for marketplace engagements later).
- **D-07:** All Project / Board values extracted to top-of-file constants in `provisioner.service.ts` for one-line iteration. Verbiage strings already partially extracted; extend the constants block for workspace Project + Board values.

### Governance verification gate (Engagement Task drop) — Q1

- **D-08:** **SPECULATIVE-DROP.** Drop `aha1-N` Engagement Task from the recipe in this phase. UAT smoke verification deliverable (Plan 0X): provision a fresh test org, then confirm ZB Platform Governance UI renders the new `platform.Project` record.
  - **If verified:** drop is final; close gate.
  - **If not verified:** fall back to placeholder Task with backlog entry `[GOVERNANCE-PROJECT-RENDERING]` to remove the placeholder once Governance ships Project rendering.

### Vetting Board — Q2

- **D-09:** Vetting Board `boardType='list'` (checkbox-shape). Vetting requirements are paired req-sat tasks; satisfied/not is the primary state. Multi-stage transitions are not in v1.4 scope.
- **D-10:** Vetting Board `isDefault=false`. Workspace default Board (the kanban one) keeps `isDefault=true`. Server enforces at-most-one-default-per-parent.
- **D-11:** Vetting Board lazy-created on first vetting requirement; NOT eagerly created in the platform-engagement provisioning recipe. Marketplace engagement provisioning (post-v1.4) may eager-create.
- **D-12:** Vetting paired-task shape: **(γ) parent + one subtask per side**. `activityId` on parent ties to vetting workflow definition. Subtasks inherit parent's board via server-default chain. Single-side requirements collapse to parent-only.

### Schema retirement — Q3

- **D-13:** Schema repo PR (Daniel Rojas review): **DEPRECATE WITHOUT DELETE.** Keep `Engagement`, `EngagementVettingItem`, `SmeMartProject` class definitions in the schema package; stop CREATING new records (provisioner moves to `platform.Project.create`); dual-read path until data ages out.
- **D-14:** During Plan 01 inventory, confirm with Daniel Rojas / Nic that schema-class-with-no-new-writes orphan reads remain functional. If lifecycle semantics surface a problem, escalate before merging the schema PR (pre-merge gate).
- **D-15:** Existing W3Geekery + Auditmation Dev demo data continues to be readable through `SmeMartProject` GQL paths during the dual-read window. Read paths consume both `platform.Project.list` AND existing GQL `SmeMartProject` until data ages out. NOT a one-shot migration. File `SCHEMA-RETIREMENT-DELETE-1` (Medium) post-29.5-closure for the eventual class-deletion follow-up — gated on dual-read having zero remaining readers, not a calendar date.
