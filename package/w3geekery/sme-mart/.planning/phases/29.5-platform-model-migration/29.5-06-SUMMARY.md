## Observations / Surprises

### Observation 1 — `parentId` is omitted from get response, not returned as `null`

The Engagement Project (depth 1, `parentId=null` semantically) returns a payload **without** a `parentId` field at all rather than `{"parentId": null}`. Functionally equivalent for null-checks like `obj.parentId == null` (which is true in both cases under JS coercion), but strict `=== null` checks would fail on the absent variant. This affects:
- Any consumer using `=== null` to detect top-level Projects. Use `!parentId` or `parentId == null` instead.
- Spec assertions that check `expect(parentId).toBeNull()` (the Plan 02 v3 spec uses `.toBeNull()` — should be `.toBeFalsy()` or `.toBeUndefined()` for round-trip consistency). Not a code bug — the spec asserts on the `create` request body, which still passes `parentId: null` explicitly.

**Action:** Low-priority — flag in 29.5-WAVE-2-CLOSE.md follow-ups. Not blocking.

### Observation 2 — D-48 cascade mechanism

Project Lead is added **explicitly per Project** at creation time, not resolved via parent-chain at query time. Both depth-1 and depth-2 Projects return Clark in their direct `listMembers` response. This means:
- Lead inheritance is materialized, not lazy. Renaming/transferring Lead at depth 1 will NOT automatically propagate to depth 2 (each is a separate membership record).
- For SME Mart "who is the Lead?" lookups, you can query either Project directly — no need to walk parents.

**Action:** Worth documenting in `.planning/notes/zb-task-reference.md` as a Lead-mechanism note. Director should confirm this matches the v1.4 spec intent (the original D-48 language doesn't distinguish materialized-vs-lazy).

### Observation 3 — Auto-Board naming + description pattern

Auto-Board name: `"{projectName} Board"` (with explicit space).
Auto-Board description: `"Default board for {projectName}"`.

Both depths show the same pattern:
- Engagement auto-Board: `"W3Geekery <- ZeroBias Board"` / `"Default board for W3Geekery <- ZeroBias"`
- Project tier auto-Board: `"ZeroBias Platform Board"` / `"Default board for ZeroBias Platform"`

v1.4 spec says we accept the auto-Board name without rename. **Confirmed working.** No rename call needed.

### Observation 4 — D-49 namespace drift between code and live UAT artifact

**This is a real correctness concern flagged for Director handoff.**

- **Live UAT artifact:** Engagement tag name = `sme-mart.engagement.zerobias-to-w3geekery` (per D-49 NEW namespace; created by the manual walkthrough 2026-05-12)
- **SME Mart code:** `provisioner.service.ts` line 84 + 167 probes/creates with the LEGACY namespace pattern: `` `sme-mart.eng.${PLATFORM_SUPPLY_SLUG}-to-${slug}` ``

**Consequence:** If SME Mart's `isOrgProvisioned(W3Geekery org)` runs on UAT today, it searches for tag `sme-mart.eng.zerobias-to-w3geekery` — that tag doesn't exist (the live tag is in `.engagement.` namespace) — probe returns false — onboarding guard routes Clark to the holding page even though the org IS provisioned.

**This is NOT a Plan 06 bug.** D-49 namespace flip was correctly out-of-scope for the Plan 02 v3 amendment (the surgical 5 changes per the Director's confirmation list (a)-(e) did not include namespace migration). It IS a follow-up that must land before Phase 31 (re-provisioning exercise) and before any UAT user-facing onboarding flow goes live.

**Director-handoff item — proposed backlog `D-49-NAMESPACE-MIGRATE-1`:**

1. Update `provisioner.service.ts` constants + JSDoc to use `sme-mart.engagement.*` for the engagement-identity tag namespace.
2. Update `isOrgProvisioned` probe to either:
   - (a) Probe BOTH namespaces (legacy `.eng.` + new `.engagement.`) and union the results — preserves UUID stability for legacy tags; OR
   - (b) Probe only the new namespace and accept that legacy-provisioned orgs (if any exist via SME Mart code path on UAT prior to this fix) need a one-time tag rename or re-provisioning.
3. Decide: are there any orgs on UAT currently provisioned via SME Mart code (legacy namespace) that need backfill? The W3Geekery UAT artifact was created by manual walkthrough, not by code, so it's already in the new namespace.

Empirical state check (informational): the legacy `sme-mart.eng.w3geekery-default-zb` tag (a81cd320-...) exists on UAT per the Director's handoff but is from an **earlier** provisioning attempt and is NOT linked to the current Engagement Project. So at present there are zero "legacy-namespace + active-engagement" orgs on UAT. Path (b) is viable for now.
