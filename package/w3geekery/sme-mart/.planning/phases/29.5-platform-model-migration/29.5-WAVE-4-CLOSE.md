### 3. PARENT-ID-NULL-SHAPE-NOTE (Low severity — SDK shape note)

**What:** `platform.Project.get` response **omits** the `parentId` field entirely for top-level Projects (`parentId=null` at create time), rather than returning `{"parentId": null}`. Strict `=== null` checks in consumer code would fail; `== null` and `!parentId` both work.

**Where it surfaces:** The Plan 02 v3 spec uses `.toBeNull()` on the create-request `parentId` arg (still passes because we assert on what we sent, not what we get back). No code bug today. Worth noting for any future round-trip assertions.

**Action needed:** None urgent. Could land as a one-line comment in `provisioner.service.ts` JSDoc or a SDK gotchas note. Low priority.

### 4. D-48-LEAD-MECHANISM-SPEC-CLARIFY (Low severity — spec clarification)

**What:** D-48 says "Project Lead inherits down the parentId chain." Empirical mechanism on UAT is **eager-materialized-per-Project**: each Project created has its creator explicitly added as Project Lead, not resolved via parent-chain at query time.

**Implication:** Renaming/transferring Lead at depth 1 will NOT automatically propagate to depth 2 (each Project has its own membership record). SME Mart "who is the Lead?" lookups can query either Project directly — no parent-walking needed.

**Action needed:** Director should confirm this matches v1.4 spec intent. If yes, update D-48 language in DECISIONS.md to say "Project Lead is materialized on each Project at creation by the auto-Lead behavior of `platform.Project.create`. Same person ends up Lead at every depth, matching the inheritance outcome via eager materialization."

If Director believes D-48 intended TRUE lazy inheritance (where depth-1 Lead change propagates to depth-2), this is a platform spec mismatch worth flagging to Nic.
