# Phase 29.5 Plan 07 — UAT Vetting Board Smoke

**Headline: Plan 07's premise does NOT match current SME Mart code architecture. No assertion failure to report — but no assertion passes either. The plan needs reframing or deferral. Routing to Director.**

This is NOT a SME Mart bug, NOT a platform bug, and NOT a spec mismatch in the v3 recipe. It's a **plan-vs-current-architecture mismatch**: Plan 07 was authored before the v3 amendment landed; v3 obsoleted Plan 07's core premise.

---

## What Plan 07 expected

Per `29.5-07-PLAN.md` and the Wave 4 dispatch:

> "Vetting Board lazy-create path. On UAT in W3Geekery context, trigger the vetting flow that creates a vetting Board (per D-12: boardType='list', isDefault=false, lazy-created on first vetting requirement)."

The plan expected:
- A `platform.Board` primitive (`boardType="list"`, `isDefault=false`) attached to the engagement Project, created lazily on first vetting requirement.
- A paired-task (γ) shape: parent vetting `platform.Task` on that Board + one subtask per side (buyer + provider) with parentTaskId set.
- SME Mart Vetting view consuming `platform.Board` + `platform.Task` via SDK.


Current vetting flow:
- **Read path:** `vetting.service.listVettingItems(engagementId)` issues a GQL query against the legacy `EngagementVettingItem` class.
- **Write path:** `vetting.service.initializeVetting / createVettingItem` issues `PipelineWriteService.pushEntities('EngagementVettingItem', ...)` — Pipeline.receive on the W3Geekery-owned `EngagementVettingItem` AuditgraphDB class.
- **No `platform.Board` lazy-create exists in code.** The Board referenced in D-12 / Plan 07 is not yet wired up.

## Why this happened

Plan 07 was authored before the v3 amendment landed (commit `523e924`, 2026-05-12). The original Plan 02 included Step F (`ensureDefaultBoard`) which created a Board explicitly. Plan 07 was sized to verify a downstream "vetting Board" was being created on top of that. The v3 amendment dropped Step F entirely (auto-Board from `platform.Project.create` is accepted) and never replaced the vetting-Board concept with a current-code equivalent.

The decision document `D-12` (referenced by Plan 07) describes the lazy-create vetting Board pattern as a forward-looking architecture decision. **No phase in the current v1.4 roadmap implements it**, and the v3 amendment did not pull it in (correctly out-of-scope per the 5 surgical changes).

The existing SME Mart vetting flow continues on the legacy GQL `EngagementVettingItem` path. That path still works at the SDK level (Pipeline.receive against a real AuditgraphDB class) and at the UI level (the Vetting view component renders it). Neither side currently touches `platform.Board` / `platform.Task`.

## Options for Director

Plan 07 has three plausible resolutions; routing to Director for selection:

### Option A — Defer Plan 07 to a future migration phase (recommended)

- Mark Plan 07 status as **DEFERRED / PREMISE-OBSOLETE** for v1.4.
- File a v1.5 (or appropriate later milestone) backlog entry: `VETTING-PLATFORM-MIGRATE-1` covering both (a) migrate vetting items off GQL `EngagementVettingItem` to `platform.Task` + (b) introduce the vetting `platform.Board` lazy-create per D-12.
- Wave 4 close acknowledges that Plan 07 verification did not run because the premise was obsoleted by the v3 amendment.
- No Wave 4 blocker — Plan 06 SDK assertions are the substantive verification.

### Option B — Reframe Plan 07 to verify current (GQL) vetting flow

- Reframe Plan 07 to verify the legacy GQL vetting path (the actual current code) instead of the forward-looking platform.Board path.
- Lose the SDK contract assertions for `platform.Board` + paired `platform.Task` (because they're not what code does today).
- Risk: this normalizes legacy GQL as a long-term plan deliverable, which contradicts the D-08 / D-46 direction of "everything moves to platform primitives over time."
- Not recommended unless we explicitly want to lock-in the legacy path for v1.4.

### Option C — Add Plan 07's premise to the implementation backlog inside Phase 29.5 itself

- Insert a new plan (e.g., 29.5-09) that **implements** the vetting `platform.Board` lazy-create + paired `platform.Task` shape so Plan 07 can verify it.
- Estimated scope: medium-to-large. Requires `vetting.service` rewrite, new SDK call paths, Vetting view rendering updates.
- Pushes Phase 29.5 timeline. Not recommended unless v1.4 demo / sale specifically needs the platform-Board vetting path.

**Default recommendation:** Option A. Defer + backlog. v1.4 doesn't need vetting-on-platform-Board to ship; the legacy GQL path is functional. Phase 29.5's primary v1.4 deliverable (engagement + project-tier on platform.Project, with auto-Board + auto-Lead) is fully validated by Plan 06.
