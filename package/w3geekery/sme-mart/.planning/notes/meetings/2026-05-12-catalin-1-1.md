## Topics Discussed

- **Three-org topology** — Customer/dev org (Undefined / SDI / Geekery) is its own org. ZeroBias Platform is its own org. ZeroBias Community Guild (a.k.a. "Zerobias Org") is its own org. A user from a dev org is a CUSTOMER of the Platform org AND a MEMBER (not owner) of the Guild org.
- **Two default engagements per user**, both auto-provisioned:
  - **Engagement A — Customer ↔ Platform.** Default project where dev org and ZeroBias Platform interact (tasks, needs, work streams). This is what Clark is building today in v1.4.
  - **Engagement B — Member ↔ Guild.** SEPARATE default project as a Guild member. Distinct from Engagement A.
- **Guild has multiple opt-in projects.** Beyond the default Guild engagement, users browse a list of Guild projects and opt into ones where they want to collaborate (e.g., a "connectors project" with Dan / Joe / Ragu as peer contributors).
- **Guild eligibility / classification** — Guild membership is reserved for: small companies, nonprofits, government, hospital institutions, not-for-profit entities. Public companies, PE-funded companies, large privately held companies are NOT Guild members. They live by enterprise/non-guild rules.
- **Content development & publish flow (4-stage promotion):**
  1. **Local** — build in your own org (private dev iteration).
  2. **Guild project** — develop collaboratively with other Guild members; multi-stage consensus required.
  3. **Zero Bias Org catalog** — Guild publishes to Guild/Org catalog via consensus including Platform people (Brian, Kevin, Nick).
  4. **Global catalog** — Additional consensus + review → publish to global catalog (universal consumer access). Includes ALL parties (not just Guild members).
- **Private orgs (non-Guild, e.g., enterprise) can publish content** but they pay for it. Same publish process; different economic model. "Decision all the time: publish private (pay) or contribute to Guild (free)."
- **Catalin's mental model proposal — branches-per-stage.** "In Zerobias org we will have the branches for each stage of the content. … local → PR against dev branch of zerobias org → after consensus, merge → next stage Zerobias org catalog." Brian: "Correct."
- **Urgency** — "We have no choice. This is like the next month we have to have this land." Brian wants Catalin to share the transcript/audio/summary with Chris, Kevin, Nick, Clark, Dan and confirm everyone's aligned. Catalin asked if Kevin is aligned; Brian: "We should be. SME Mart's BACKLOG `028-ORG-AUTO-ENGAGEMENT` (item 5 from 5/5 meeting) tracks the dual-engagement requirement. v1.4 Phase 27 currently provisions only the Platform engagement; the Guild engagement is the missing half.

The Guild catalog promotion is a strong concrete use case for that primitive.

1. **v1.4 platform-engagement provisioner only provisions Engagement A (Customer ↔ Platform).** Engagement B (Member ↔ Guild) is NOT provisioned anywhere in current SME Mart code. This is a real gap against Brian's "two default engagements by default" rule. Options:
   - **(a)** Expand Plan 02 in-flight to provision BOTH engagements (adds 4 more SDK calls: Guild Tag + Guild Engagement Project + Guild Workspace Project + tier tag).
   - **(b)** Defer to a new Phase 32+ "Guild Engagement Provisioner" — clean separation, but means users still see only one default engagement until then.
